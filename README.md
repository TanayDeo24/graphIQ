# GraphIQ

A data science project demonstrating **unified-schema workforce analytics**: two
independent analyses — attrition risk (survival analysis) and spend anomaly
detection — running on top of one shared employee/workforce data model, with a
Postgres backend, a FastAPI service layer, and a React + Vite dashboard.

## Architecture: one shared schema, two analyses

The architectural thesis of this project is that attrition risk and spend
anomaly detection are not two disconnected datasets glued together for a demo —
they are two lenses on the **same workforce**, joined on `employee_id`.

```
                         Postgres
        ┌───────────────────────────────────────┐
        │  employees  (real IBM HR data)          │
        │      │                                  │
        │      ├── comp_history                   │◄── attrition risk
        │      ├── performance_reviews             │    (survival analysis)
        │      ├── benefits_enrollment              │
        │      │                                  │
        │      └── expense_transactions ───────────│◄── spend anomaly
        │           (department_id too)            │    detection
        └───────────────────────────────────────┘
                         │
                    FastAPI layer
              (reads precomputed result
               tables only — no on-the-
                  fly computation)
                         │
                 React + Vite dashboard
              (AttritionPage, SpendPage)
```

Every table joins back to `employees.employee_id` (the IBM dataset's
`EmployeeNumber`). `expense_transactions` also carries the same 36-month
window and the same 1,470 employees as `comp_history` — the spend generator
deliberately reuses the attrition component's window helper
(`window_length_months`) rather than inventing its own timeline. Both
components' EDA and model-evaluation scripts query Postgres directly (never
the raw generated CSVs), and the FastAPI layer only ever reads precomputed
result tables — nothing is computed at request time.

## Data provenance and generation methodology

**Real, public, cited:** `employees` is loaded unmodified (columns renamed to
snake_case only) from the
[IBM HR Analytics Employee Attrition & Performance dataset](https://www.kaggle.com/datasets/pavansubhash/ibm-hr-analytics-attrition-dataset)
(1,470 rows, 35 columns), a synthetic-but-widely-used public benchmark
dataset commonly used for HR analytics demonstrations.

**Fully synthetic, disclosed:** every other table —
`comp_history`, `performance_reviews`, `benefits_enrollment`, and
`expense_transactions` — is generated by
[`src/generation/attrition_extension.py`](src/generation/attrition_extension.py)
and
[`src/generation/spend_generator.py`](src/generation/spend_generator.py).
Nothing in these tables is drawn from or claims to represent any real
company's actual compensation, performance, or spend data.

Key generation choices (each documented in-line in the source):

- **36-month history, backward-consistent.** Each employee's synthetic
  compensation path is built backward from their real, static
  `MonthlyIncome` so the final logged value always matches the known real
  number exactly.
- **Temporal train/test split.** Not a random 80/20 — see
  `assign_temporal_split()`. (The attrition model-fitting code goes one step
  further and uses a standard rolling-origin design for the same underlying
  reason; see the "why" note below.)
- **~420,000 synthetic expense transactions**, lognormal amounts per
  merchant category, department-skewed category mix and frequency, documented
  in `spend_generator.py`'s module docstring.
- **Anomaly injection at a primary 5% rate** (with 1%/10% variants generated
  for robustness testing), concentrated 70/30 between a designated 10% of
  employees and the rest — mirroring how real spend abuse clusters rather
  than distributing uniformly — across three distinct, disclosed anomaly
  types (`point_spike`, `slow_drift`, `coordinated_pattern`).
- **Automated validation** (`src/generation/validate_synthetic.py`) checks
  generated distributions against their own documented target parameters and
  flags unintended correlations; see
  [`data/generated/validation_report.md`](data/generated/validation_report.md)
  after running the generation step.
- **`duration_months` (attrition survival target) is month-level-resolution,
  not the real dataset's own resolution.** The real `YearsAtCompany` field is
  annual-resolution only (integer years) — using it directly (`tenure_years *
  12`) gave only ~37 distinct duration values across 1,470 employees, heavy
  ties that degenerated the lead-time metric to a median of 0 months and made
  the four 30/60/90/180-day AUC horizons numerically identical.
  `assign_fine_grained_duration()` in `attrition_extension.py` derives a
  disclosed, reproducible month-level value instead, anchored to each
  employee's own already-generated `comp_history` timeline (196 distinct
  values after the fix). The real annual value is never overwritten — it
  stays available as `tenure_years` throughout. See the "Attrition" results
  section below for what this fix did and did not resolve.

## Honesty / scope disclaimer

This project demonstrates **methodology and evaluation rigor** — survival
analysis done properly (proportional-hazards checking, time-dependent AUC,
calibration by segment, bootstrapped confidence intervals), and anomaly
detection done properly (per-type precision/recall, dollar-weighted impact,
detector robustness across injection rates). **It is not a real finding about
any specific company**, including Rippling or any other employer. All data is
either a cited public benchmark dataset or disclosed synthetic data.

The counterfactual sensitivity analysis in the attrition component
(`GET /api/attrition/sensitivity`) is **correlational, never causal**. It
answers "how does this model's predicted risk score move if we simulate a
10% income increase," not "what would happen to this employee's actual
attrition probability if they received a raise." This framing is enforced in
the code (`SENSITIVITY_DISCLAIMER` constant, reused in the evaluation script,
the API response payload, and here) — never as "predicted effect of a raise."

## Setup instructions

Run these in order from a fresh clone.

```bash
# 1. Start Postgres (Docker, if you have it — see note below if not)
docker-compose up -d

# 2. Python environment
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 3. Download the real IBM dataset (needs a Kaggle API token at
#    ~/.kaggle/kaggle.json or ~/.kaggle/access_token) — or download it
#    manually from the Kaggle URL above and place the CSV at data/raw/
kaggle datasets download -d pavansubhash/ibm-hr-analytics-attrition-dataset -p data/raw --unzip

# 4. Generate all synthetic data + validate it
python -m src.generation.attrition_extension
python -m src.generation.spend_generator
python -m src.generation.validate_synthetic

# 5. Load everything into Postgres (also applies sql/results_schema.sql)
python -m src.db.load_to_postgres

# 6. Run EDA (writes plots to data/generated/eda_outputs/)
python -m src.eda.attrition_eda
python -m src.eda.spend_eda

# 7. Fit models + run every required evaluation metric, write results to Postgres
python -m src.models.attrition.evaluate
python -m src.models.spend.evaluate

# 8. Run the API
uvicorn src.api.main:app --reload
# -> http://localhost:8000/docs

# 9. Run the dashboard (separate terminal)
cd dashboard
npm install
npm run dev
# -> http://localhost:5173
```

Copy `.env.example` to `.env` first and adjust if your Postgres credentials
differ from the defaults.

**If you don't have Docker:** any local Postgres 16 works — create a database
and user matching your `.env`, then run `psql -f sql/schema.sql` against it
before step 5 (`load_to_postgres.py` applies `sql/results_schema.sql`
automatically). This repo was built and verified against a local
Homebrew-installed Postgres 16 rather than Docker, since Docker wasn't
available in the build environment; `docker-compose.yml` is provided and
unmodified from the spec for anyone who does have Docker.

## Headline evaluation results

Numbers below are from a run against the real IBM dataset + the generated
5% injection-rate spend dataset; see `data/generated/attrition_outputs/` and
`data/generated/spend_outputs/` for full artifacts (including every bootstrap
CI, per-segment calibration row, and per-transaction explanation).

### Attrition (survival analysis)

| Metric | Value |
|---|---|
| Cox PH concordance index | 0.964 |
| GBM survival concordance index | 0.921 |
| GBM integrated Brier score | 0.091 |
| GBM time-dependent AUC: 30d / 60d / 90d / 180d | 0.916 / 0.954 / 0.952 / 0.967 |
| GBM mean time-dependent AUC | 0.959 |
| PH assumption violations (Schoenfeld residual test, p<0.05) | none |
| Lead time, true positives: mean | 3.4 months (95% CI 2.7–4.0, n=84) |
| Lead time, true positives: median | 3.0 months (95% CI 1.5–4.0, n=84) |
| Distinct `duration_months` values (1,470 employees) | 37 → 196 after the fine-graining fix |
| Counterfactual sensitivity (simulated +10% income, GBM) | mean risk-score change −1.2%; 32% of the high-risk sample decreased, correlational only |

**What the duration-granularity fix actually resolved, and what it didn't —
reported honestly, not adjusted to look better:**

- **Resolved:** the four AUC horizons are now genuinely distinct values
  (0.916 / 0.954 / 0.952 / 0.967), not the identical number reported before.
  This was a real consequence of annual-only duration ties and is fixed.
- **Resolved:** the lead-time distribution is no longer degenerate. Median
  went from 0.0 months (95% CI 0.0–0.0, meaningless) to 3.0 months (95% CI
  1.5–4.0, a real distribution — see the histogram on the dashboard).
- **Not resolved, and this fix could not have resolved it:** concordance and
  AUC remain implausibly high relative to published real-world attrition
  C-index literature (typically 0.65–0.80) — Cox barely moved (0.966 → 0.964)
  and GBM's concordance and integrated Brier score both got *worse*
  (0.909 → 0.921 concordance; 0.067 → 0.091 IBS, higher is worse) after the
  fix, not better. Investigating why turned up the actual cause: **`features.py`
  sets `tenure_months = duration_months` (line 81) and includes `tenure_months`
  in the model's own input feature set (line 18)** — both survival models are
  trained with a copy of their own prediction target as an input feature. That
  is direct label leakage, and it fully explains the implausible discrimination
  regardless of duration granularity; fine-graining the leaked value made the
  leak *more* precise (fewer ties diluting it), which is why GBM's numbers got
  slightly worse, not better, after the fix. This is a separate, pre-existing
  bug, out of scope for the two problems this fix request diagnosed — it is
  **not fixed here** and is flagged as the clear next thing to fix
  (`src/models/attrition/features.py:81` and `:18`).

### Spend (anomaly detection)

| Metric | Value |
|---|---|
| Ensemble precision / recall / PR-AUC (overall, 5% injection) | 33.7% / 33.6% / 0.317 |
| Top 10% of alerts capture (dollar-weighted gains) | 79.2% of flagged dollar volume |
| Alerts per 1,000 transactions (operating threshold) | 50.0 |
| CUSUM drift detection delay: mean | 7.3 months (95% CI 4.3–10.7, n=15 detected cases) |
| CUSUM drift detection delay: median | 5.0 months (95% CI 4.0–9.0, n=15 detected cases) |
| `slow_drift` cases ever detected by CUSUM | 15 of 579 (2.6%) |
| Of those detected: caught while still active / only after it ended | 73% / 27% |
| Robustness (1%/5%/10% injection) | `point_spike` PR-AUC stable ~0.46–0.59 across all three rates; `slow_drift`/`coordinated_pattern` stay low at every rate for every detector, CUSUM included |

**Standalone PR-AUC per detector, per anomaly type** (not just the ensemble —
the comparison table this fix request asked for, and the actual interesting
result; also live on the dashboard's Spend page):

| Detector | `point_spike` | `slow_drift` | `coordinated_pattern` | overall |
|---|---|---|---|---|
| Isolation Forest | 0.896 | 0.028 | 0.039 | 0.417 |
| Autoencoder | 0.863 | **0.051** | 0.080 | 0.464 |
| CUSUM | 0.068 | 0.021 | 0.018 | 0.084 |
| Ensemble | 0.588 | 0.032 | 0.038 | 0.317 |

**This does not support the "CUSUM catches what point detectors structurally
can't" framing this project originally shipped with, and that framing has
been removed rather than kept.** Reported plainly: CUSUM's own standalone
`slow_drift` PR-AUC (0.021) is the *lowest* of all four detectors — including
Isolation Forest (0.028) and the autoencoder (0.051), the two detectors it
was specifically meant to outperform on this anomaly type. The autoencoder is
actually the best standalone `slow_drift` detector in this run. CUSUM's
overall PR-AUC (0.084) is also the worst of the four. Beyond precision/recall,
CUSUM only ever flags 15 of the 579 injected `slow_drift` cases at all
(2.6%) — the other 564 are never detected by CUSUM regardless of delay. Of
the 15 it does catch, 27% are only caught after the drift has already ended
(the mean 7.3-month delay is close to or longer than the injected drift's own
4–8 month duration), which undercuts the "catches it early" framing on its
own terms even before the detection-rate problem.

None of the CUSUM tuning (`k=0.5σ`, `h=5σ` in `cusum.py`) was adjusted to
produce a better-looking number here — these are the results of the existing,
documented Western-Electric-style tuning, reported as measured. A real fix
would need to revisit either the CUSUM tuning itself, the `slow_drift`
injection parameters (see `spend_generator.py`'s `SLOW_DRIFT_TOTAL_INCREASE_RANGE`),
or both — that investigation is out of scope for this fix request.

```
src/api/                 FastAPI service layer
dashboard/               React + Vite + recharts frontend
data/raw/                 the real IBM dataset (committed, small, no auth needed to reproduce)

```
